# OPERATIONAL CONSTRAINTS:
1. RESPONSE STYLE: Krótko, zwięźle. Język polski.
2. CODE: Always English. Full files only. Include filename as H3 header.
3. COMMAND EXECUTION: Wszystkie komendy systemowe formatuj/opisuj tak: bash -c "command".
4. CONFIRMATION: Zawsze pytaj o moją zgodę przed wykonaniem destrukcyjnych działań na repozytorium.
5. CONFIRMATION & SAFETY:

6. DOCKER COMPOSE COMMAND: do uruchomienia docker compose zawsze uzywaj komendy: docker compose -f <FILENAME> <FLAGS>
7. DEV ENVIRONMENT DEPLOYMENT: 
   - do deplojowania aplikacji na srodowisku DEV uzywaj lokalnego klastra (Docker desktop K8s)
   - konfiguracja: tmp-gemini/my-values.yaml
   - buduj obrazy lokalnie i automatycznie inkrementuj tagi (v1, v2, v3...) na podstawie ostatnio zbudowanego obrazu
   - przed deplojem wykonuj `helm lint ./charts/k-view`
   - po deploju czekaj na `kubectl rollout status deployment/k-view`
   - usuwaj poprzednio używany tag obrazu lokalnego po udanym wdrożeniu nowej wersji
   - uzywaj flagi: --set image.tag: v[N] (zgodnie z wykrytym numerem)
   - wdrazaj do namespace: k-view
   - nazywaj obraz zawsze: k-view

# VERSIONING & BUILD RULES:
1. VERSION BUMP: Jeśli napiszę "podbij wersję (fix/feat/!)":
   - Najpierw sprawdź obecną wersję (np. w package.json, VERSION lub tagach git).
   - Sprawdzaj i aktualizuj wersje w: web/package.json, charts/*/Chart.yaml (version i appVersion) oraz charts/*/values.yaml (image.tag)
   - Podbij odpowiedni numer zgodnie z SemVer:
     * fix -> patch (0.0.x)
     * feat -> minor (0.x.0)
     * ! -> major (x.0.0)
2. COMMIT FILES: dodawaj do stage tylko te pliki w ktorych zrobiles zmiany
3. COMMIT MESSAGE:
